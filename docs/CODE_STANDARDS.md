# 程式標準

整個版本庫共用的設計、審查與改造規則，適用於所有語言。這裡只寫原則與判斷標準；各部分特有的寫法另有文件（`ml/` 見 [../ml/CONVENTIONS.md](../ml/CONVENTIONS.md)），目錄與依賴方向見 [../AGENTS.md](../AGENTS.md)。新程式照這裡寫，舊程式在修改時順便改成這樣。

## 設計

1. **職責**：一個型別、一個模組只負責一件事。判斷方式是把它承擔的職責列成表，每列寫出對應的程式；表上有幾件互不相干的事，就要切開。切分依據是資料擁有權與不變條件（哪些資料必須一起保持一致、由誰維持），不是行數。拆開後各部分只透過方法互動。
2. **狀態**：讓不合法的狀態寫不出來。彼此相依的旗標、索引與可選值合成一個型別；可以同時成立的保留成欄位，互斥的才用列舉。索引只由擁有清單的型別修改，取用經由回傳可選值的方法。平行的容器合成一個元素型別的容器。每組狀態的不變條件寫在型別旁，並以斷言或測試驗證。
3. **設定與快取**：影響計算結果的設定只能經 setter 修改，setter 負責讓快取與衍生值失效。同一類設定合成一個結構一次設定。快取的鍵包含所有影響結果的輸入。衍生值和來源由同一處更新。有不變條件的資料結構不公開可寫欄位。
4. **信任邊界**：外部資料（模型輸出、跨語言介面、檔案、使用者設定、命令列參數、外部行程）進入時驗證一次，之後的程式可以信任它。檢查長度、範圍、空值、有限值與編碼；不合格時走「沒有這份資料」的路徑或明確報錯，不 panic。
5. **錯誤**：失敗要讓呼叫端知道。寫入、刪除、複製、外部行程失敗時，不只印出記錄就回報成功。「待寫入」「已完成」這類標記在動作成功後才更新。刻意忽略的錯誤，旁邊寫一行原因。
6. **副作用**：查詢與轉換用的函式只讀輸入、回傳結果。修改狀態、寫檔、送出、通知集中在少數幾處。
7. **依賴與擴充**：依賴只能沿 AGENTS.md 的方向。新功能用新增模組或登記的方式加入，不在大型分派裡加分支。能力由外部注入。介面、trait、protocol 只在有兩個以上實作、需要替換依賴或測試替身時才加；不為了符合原則或套用設計模式而增加結構。
8. **事件驅動的元件**：以「狀態 + 事件 → 轉移 + 效果」組織。協調者分派事件，細節放在擁有資料的元件；每個分支呼叫具名的方法；效果和轉移分開，才能單獨測試與重播。
9. **熱路徑**：每次按鍵、每次重繪執行的程式，新增工作前先量 p50／p95／p99 並記錄。只在特定時機需要的計算延到那時再做。
10. **大小**：函式超過約 150 行就拆；一個檔案一個主要職責。為了和參考實作逐行對照而保留的長函式，註解寫明原因。
11. **測試**：先測不變條件與連續事件後的狀態；有參考實作就做差分比對；空集合、單一元素、最後一頁、非有限值、損壞的檔案各一個測試。不寫照抄實作的測試。

## 語言

- **Rust**：fmt、clippy（`-D warnings`）、test、deny 零警告；不新增 `allow` 來壓過長度與 bool 數量的 lint。浮點排序用 `total_cmp`。來自外部的長度與位移用 checked 運算與 `get()`。`unsafe` 寫 `// SAFETY:` 說明前提由誰保證。會失敗的操作回傳 `Result`／`Option`。
- **Swift**：屬性預設 `private` 或 `private(set)`。資料用 struct，擁有生命週期的元件用 class；每份 UI 狀態只有一個擁有者。索引前確認範圍，不寫空陣列會溢位的 `count - 1`。解碼的資料先驗證再用。`try?` 只用在失敗不影響結果的地方。畫面的建立與版面計算、狀態轉移分開。
- **Python**：見 [../ml/CONVENTIONS.md](../ml/CONVENTIONS.md)。

## 審查

### 評分

七個面向各給 1–5 分，只針對讀過的程式；沒有執行測試、量測或讀完全部檔案時要寫明。

| 面向 | 5 分 | 1 分 |
|---|---|---|
| 功能邏輯完整度 | 邊界情況都有處理 | 有可觸發的錯誤 |
| 可讀性與命名 | 第一次讀就懂意圖 | 名稱誤導或缺少說明 |
| SOLID 原則 | 職責單一，擴充靠新增模組 | 核心型別承擔多種不相干的職責 |
| 模組化與低耦合 | 只經公開方法互動 | 改一處要同時改好幾處 |
| 狀態管理 | 不合法的狀態寫不出來 | 大量相依的可變欄位，靠人記得 |
| 擴充彈性 | 新功能加模組或登記即可 | 新功能要改多個核心型別 |
| 可測試性 | 轉移與轉換可以單獨測試 | 副作用與邏輯混在一起 |

### 嚴重度

| 等級 | 意思 |
|---|---|
| P0 | 正常使用就會遺失資料、當機或洩漏隱私 |
| P1 | 能從程式碼指出觸發條件的錯誤或不一致 |
| P2 | 維護風險：現在正確，但依賴遠處維持的條件 |
| P3 | 可以改善 |

每項發現寫出位置、關鍵片段與觸發條件；分清實際錯誤與維護風險，正常路徑不會觸發的寫明由誰保證；沒讀程式確認的標「未確認」。看起來像問題但合理的地方也列出理由。

### 報告

報告放在 `docs/reviews/<日期>-<範圍>.md`，記錄當天的程式，之後不隨程式更新。段落：範圍與方法、總評與評分、職責表、狀態與不變條件、SOLID 逐項、發現、合理之處、改造順序。

修改的審查逐項確認：職責是否加重、是否新增相依卻分開存放的狀態、設定是否讓快取失效、外部資料是否驗證與失敗是否回報、是否有依賴遠處條件的索引、轉換函式是否修改狀態、熱路徑是否增加工作、是否有超過 150 行的函式。

## 改造

1. 先補不變條件與測試，再動結構。
2. 一次一步，每步可以單獨審查與回退。
3. 不改行為的改造必須和改造前的輸出完全相同（引擎的比對方式見 AGENTS.md）。
4. 修正錯誤和改造結構分開提交；會改變輸出的修正附上評測與研究紀錄。
5. 同一次修改更新相關文件。
6. 順序：不變條件與測試 → 設定與快取的一致性 → 合併相依的狀態 → 移出純轉換 → 拆出獨立模組 → 重整事件分派 → 評估完整的狀態轉移架構。
