# 相關工作與比較

注音輸入法有很長的開源傳統：新酷音（libchewing）、小麥注音（McBopomofo）、RIME 等專案累積了詞庫、讀音與組字的大量經驗。2026 年有兩個專案把研究過程完整公開：

- 靈犀注音（0c）發表了技術報告與兩個模型。
- 善解（shanjie）公開了研究紀錄、實驗合約與評測集。

這些公開的材料讓不同做法可以被檢驗、被重現，對整個領域很有價值。我們從中學到很多，在此致謝。

這份文件的內容：

- 兩個專案的做法
- 我們從中學到、實際採用了什麼
- 在同一批句子上的比較，以及這些數字的限制

完整的閱讀筆記在 [catalogue/](catalogue/)。

## 原則

- 目的是理解，不是排名。比較是為了看清楚不同設計的取捨，以及找出我們自己的不足。三個專案的設計目標不同，一個數字無法代表一個輸入法的好壞。
- 不複製程式碼。
  - 靈犀注音的程式是 AGPL-3.0。我們只建置、執行它來量測，只閱讀它公開的文件，不複製任何程式碼。
  - 善解是 Apache-2.0。它的評測集依各檔的授權引入並保留出處（`nlp/eval/sets/external/shanjie/`），模型檔不使用。
  - 公開的方法與結論可以學習。學到的做法都以自己的實作重寫，並在研究紀錄中註明出處。
- 數字只在註明的條件下成立。下列因素都會影響結果，表格旁都會寫出來：
  - 測試集由誰挑選、是否接近某一方的訓練資料
  - 詞庫是否涵蓋測試句的讀音
  - 寫法正規化（台／臺等）
  - 版本與設定
  - 逾時
- 引用標明來源與日期。對方的數字取自其公開文件，註明出處，不轉述成我們量到的結果。

## 兩個專案

依各專案公開的資料整理，日期為 2026-10-27。

### 靈犀注音（0c）

主要貢獻（[技術報告](https://0c.biggo.com/research/)、[模型卡](https://huggingface.co/Funmula)）：

- 以讀音為條件的語言模型重排詞圖的前幾名，並用封存的新聞測試集評估。
- 獨立的補標點模型，有明確的適用規則：送出時才補，不在段尾補。
- 兩個模型以 MIT 授權公開。
- 不打聲調模式與補全。

我們學到的：

- 「整句候選＋讀音條件」的設計是有效的方向，和我們的 v3 互相印證。
- 補標點的適用規則與評估方式，作為我們 0.5 補標點的參考基準。
- 模型逾時時退回引擎結果的保護機制（[plan.md](plan.md) A5）。

### 善解（shanjie）

主要貢獻（[GitHub](https://github.com/Nanako0129/shanjie)）：

- 完整公開研究紀錄與約 120 份實驗合約，每個改變都附成對統計。
- 只在詞圖不確定時才讓神經模型出手的門檻式融合。
- 「改選後其他字不動」。
- 安全輸入時暫停學習，以及避免 Caps Lock 切換失效的安裝方式。
- 以 CC0 釋出的開發集與使用者回報的錯誤句。

我們學到並採用的（細節見 [log.md](log.md)）：

- 成對檢定工具（`zt eval stats`）
- 重排門檻 τ
- 選字後固定其他字
- 安全輸入時不讀前文、不學習
- 升級時不重新註冊輸入法
- 引入它的評測集
- 「在維基與生成句上的進步不一定轉移到真實聊天」。這個教訓直接影響了我們聊天模型 v2 的資料選擇。

### 設計上的差異

| | 靈犀注音（0c） | 善解（shanjie） | ZhuyinType |
|---|---|---|---|
| 授權 | 程式 AGPL-3.0，兩個模型 MIT | Apache-2.0；資料多為 CC0／CC BY-SA | MIT；詞庫 CC BY-SA 4.0 |
| 引擎 | Go；詞庫＋unigram／bigram＋Viterbi | Rust；詞 bigram＋類別模型＋KN，正式語體另有 trigram | Swift；聊天、百科兩個詞 bigram 依前文混合＋個人 n-gram |
| 神經模型 | 因果 Transformer 8×512（3,261 萬參數），重排前 8 名；補標點的雙向編碼器 | 字級模型 6×384（1,440 萬參數，int8），重排前 8 名，只在不確定時出手 | 逐字模型 v3（前文＋雙向音節編碼器），分數直接進詞圖；整句重排 8×512，重排前 16 名 |
| 前文 | 最多 64 字 | 最多 2 個漢字（64 字開發中） | 讀 App 的 128 字，模型用 255 字 |
| 按錯鍵、按鍵順序 | 沒有這項設計 | 沒有這項設計 | 相鄰鍵、多按、漏按、對調、按鍵時間、個人按錯習慣 |
| 補全／Tab | 有（來自詞庫與個人片語） | 預測列 | 規劃中（0.6） |
| 補標點 | 有（送出時，段尾不補，預設關） | 沒有 | 規劃中（0.5） |
| 不打聲調 | 選用 | 沒有 | 規劃中（0.7） |
| 每鍵延遲（各自公布，量法不同） | 選字模型 P95 7–16 ms，逾時 100 ms 退回 | n-gram 每鍵 p95 約 2 ms，重排非同步 6–8 ms | 整個按鍵 p95 約 22 ms（10 音節），25 音節約 33 ms |
| 記憶體（各自公布） | 模型約 250 MB（Python worker） | RSS 約 441 MB | 常駐 29 MB（mmap） |
| 更新 | 自家下載 | Sparkle、公證、Homebrew | Sparkle（EdDSA 簽章、差分更新）、模型熱載入 |

三者的取捨不同：

- 善解的延遲最低，學習規則與發布流程最嚴謹。
- 靈犀注音有補標點、補全與不打聲調。
- ZhuyinType 把重心放在按錯鍵的容錯與長前文。

## 在同一批句子上的比較

完整的表格、設定、方法與限制在 [與其他注音輸入法的比較](../benchmarks/competition.md)（2026-10-27，ZhuyinType 0.4.0 用 App 的設定）。這裡只整理對研究方向的意義：

- 書面句子（維基百科）上 ZhuyinType 較高；口語與對話和靈犀注音差異不顯著；善解自己的開發集上和善解差異不顯著。
- 只比統計引擎時，我們在口語與對話明顯較弱（口語測試 76.3% 對靈犀統計引擎 84.5%），整套 App 的成績大部分來自神經模型。補強統計底子列為 [plan.md](plan.md) A1。
- 人名、店名、網路用語與 IT 詞彙，善解的詞包帶來很大的差距（例如店名 88% 對 26%）。這是我們沒有涵蓋的範圍，已列入規劃。
- 「使用者回報的錯誤句」上的差距主要來自按鍵容錯，反映功能範圍的不同。
- 靈犀注音的補標點模型在我們的測試段落上 precision 78.5%、recall 53.7%、F1 63.8%（門檻 0.63），是我們 0.5 補標點的參考起點。
