# ZhuyinType 模型與訓練設計

本文件說明 ZhuyinType 用到的所有「學出來的東西」：容錯通道、統計語言模型、神經選字模型、個人記憶，以及怎麼訓練、怎麼評測。產品與架構見 [DESIGN.md](DESIGN.md)。

---

## 1. 整體思路：分工，而不是一個大模型包辦

把一個大型神經網路同時拿來「猜你按錯哪個鍵」和「選字」，模型要上億參數，在 M1/M2 上也會慢。ZhuyinType 把問題拆成四層，每一層用最便宜、又夠用的工具：

```
按鍵 ─► ① 容錯通道 ─► ② 詞圖 + n-gram ─► ③ 神經選字（重排）─► ④ 個人記憶 ─► 畫面
         DP，微秒級      Viterbi，毫秒級     Core ML，約 10 ms      查表，微秒級
```

| 層 | 負責 | 為什麼這樣做 |
|---|---|---|
| ① 容錯通道 | 按鍵 → 「可能的音節 + 打錯的代價」 | 鍵盤上哪些鍵相鄰是固定的幾何事實，用加權編輯距離就算得準，不需要神經網路 |
| ② 統計 LM | 音節詞圖 → 前 16 個候選句 | 詞頻和雙詞統計又快又穩，負責「召回」：確保正確答案出現在候選裡 |
| ③ 神經重排 | 參考前文挑出最好的那一句 | 只看 16 句，不必自己生成，模型可以很小 |
| ④ 個人記憶 | 你的習慣優先 | 最便宜、效果最明顯的一層 |

關鍵設計：**③ 的輸入裡帶有 ① 的「打錯代價」**。神經網路因此能學會權衡：「這樣解讀要假設你按錯一鍵，但前文很通順」和「完全沒按錯，但不通順」，哪個比較可能。容錯和選字就這樣接在一起，不需要大模型。

## 2. 容錯通道（KeyChannel）

### 2.1 錯誤類型
| 類型 | 例子 | 備註 |
|---|---|---|
| 替換 | 想按 `j`（ㄨ）按成 `k`（ㄜ） | 只考慮實體鍵盤上距離近的鍵，代價隨距離增加 |
| 多按 | 一次碰到兩個鍵 | 多出來的鍵如果跟前後鍵相鄰，代價較低 |
| 漏按 | 少按一鍵 | |
| 對調 | 兩鍵順序打反 | 視為一次錯誤 |
| 漏聲調 | 沒打聲調就打下一個字 | 用「聲調未知」的音節表示 |

### 2.2 演算法
- 對每個「結尾鍵」，往前看 1–6 鍵的片段，跟音節表（約 1,300 個無聲調音節 × 5 個聲調）逐一算**加權受限 Damerau 編輯距離**。用帶狀 DP，片段 4 鍵以下最多容許 2 處修改，5 鍵以上最多 3 處；超過門檻就提早結束。
- 輸出每個片段的 `(音節, 通道成本, 修改次數)`。片段結果放進 LRU 快取，每鍵只需要計算新增的片段。
- 通道成本是 `-log P(按鍵 | 音節)`，由下面的參數組成：
  - `sub(d)`：依兩鍵中心距離 d 分桶（相鄰、斜對角、隔一鍵）
  - `ins_adj`、`ins_other`、`del`、`tr`、`tone_missing`

### 2.3 參數怎麼來
1. 第一版：從錯誤模擬器的設定（§5.3）直接換算。
2. 第二版：在模擬資料上對齊「真正的按鍵」和「打出的按鍵」，統計各類錯誤的發生頻率，用最大概似估計得到成本。
3. 通道與 LM 之間的權重 λ，在開發集上做格點搜尋決定。

## 3. 統計語言模型（NGramLM）

- **斷詞**：用詞庫做最大匹配初始化，再以 unigram Viterbi 重新斷詞，重複 2 輪（硬 EM）。
- **模型**：詞級 bigram，使用 modified Kneser-Ney 平滑。依熵剪枝，控制在 30 MB 以內。
- **儲存**：log 機率量化成 8 bit，存成可直接 mmap 的雜湊表二進位檔；啟動時不需解析。
- **詞庫**：每個詞記錄所有讀音；讀音用台灣標準的「本調」，因為使用者打的是本調，例如「一」打 ㄧ、「不」打 ㄅㄨˋ。

## 4. 神經選字模型（Reranker）

### 4.1 輸入格式
```
[BOS] 前文字元 ×≤64  [SEP]  音節 ×n  [OUT]  候選字 c1 … cn
```
- **前文**：游標前、已確認的文字（最多 64 字）。遇到 Secure Input 時是空的。
- **音節 token** = 聲母韻母組合嵌入 + 聲調嵌入 + **通道成本嵌入**（成本分成 0／1／2／3+ 四桶）+ **修正類型嵌入**（無／替換／多按／漏按／對調／缺聲調）。
- **輸出**：`log P(候選 | 前文, 音節)` = Σ log P(cᵢ | 前文, 音節, c<ᵢ)。
- 候選字數必須等於音節數（一個音節對一個字）。

### 4.2 架構
Decoder-only Transformer，從零訓練：RoPE 位置編碼、RMSNorm、SwiGLU，輸入與輸出嵌入共用權重。

| 版本 | 層 × 寬度 × 頭數 | FFN | 字表 | 參數量 | int8 大小 | 用途 |
|---|---|---|---|---|---|---|
| S | 6 × 384 × 6 | 1024 | 約 20k | 約 15M | 約 15 MB | 預設，M1 也輕鬆 |
| M | 8 × 512 × 8 | 1536 | 約 20k | 約 32M | 約 32 MB | 「高品質」選項 |

### 4.3 推論加速
- **前綴樹批次**：16 個候選常常前面幾個字相同。把它們排成一棵樹，用「只看祖先」的 attention mask 一次算完；結果跟逐一計算相同。
- **前文 KV 快取**：前文在同一段組字中不會變，算一次就重複使用（macOS 15 以上用 Core ML stateful model；macOS 14 改為每次重算前文，仍在時限內）。
- **時限**：40 ms 內沒回來就用統計結果，晚到的結果在請求序號仍有效時才更新畫面。

### 4.4 與統計分數融合
```
最終分數 = 統計分數 + w × 模型分數
只有當某候選的最終分數超過統計首選 τ 以上，才換掉首選。
```
w 與 τ 在開發集上校準，目標是「寧可少改，也不要改錯」：比起「本來對的被改錯」，我們寧可「本來錯的沒改到」。

## 5. 訓練流程

```
語料 ─► ① 清理 ─► ② 標音 ─► ③ 錯誤模擬 ─► ④ 預訓練 ─► ⑤ 用真引擎產生候選 ─► ⑥ 排序微調 ─► ⑦ 量化匯出 ─► ⑧ 評測
```

### 5.1 語料（只用允許再散布模型權重的來源）

| 類別 | 候選來源 | 授權（使用前逐一確認） |
|---|---|---|
| 百科 | 中文維基百科（轉台灣正體）、維基文庫 | CC BY-SA |
| 網頁 | 以 CC0 或 ODC-By 釋出的大型網頁語料（繁體子集） | CC0 / ODC-By |
| 政府 | 政府資料開放平臺的新聞稿、公報等文字 | 政府資料開放授權條款第 1 版 |
| 口語 | 群眾募集語音計畫的 zh-TW 朗讀句子 | CC0 |

- **刻意不用**：只限研究或非商業用途的資料（例如影視字幕）、論壇或社群平台上授權不明的文章、語言模型生成的對話。
- **已知弱點**：口語、網路用語偏少。用口語句子加權、提高個人記憶的權重來補償，並在評測中單獨列出口語分數。
- 所有來源記錄在 `training/SOURCES.md`；模型權重的授權依實際使用的資料決定（若含 CC BY-SA 資料，權重也以 CC BY-SA 釋出）。

### 5.2 清理與切分（①）
1. 轉成台灣正體；能取得原生繁體的來源就優先用。
2. 依句末標點切句，保留 4–64 字的句子；去除網址、程式碼、非中文比例過高的句子。
3. 用 MinHash 去重。
4. **在任何訓練開始前**先切出測試集（依來源、句長分層，約 5,000 句），再把訓練資料中跟測試句有連續 8 字相同的句子刪掉。測試集固定不變，才能公平比較每一版。

### 5.3 標音（②）
- 先用詞庫做最長匹配，詞的讀音優先於單字讀音。
- 多音字（了、著、行、長、得、重…）：訓練一個小型分類器（字 + 左右各 4 字 → 讀音），用詞庫裡讀音沒有歧義的句子當作訓練資料。
- 信心低的句子只用在預訓練的純文字任務，不進入排序微調。
- 輕聲字：語尾助詞同時接受「輕聲」和「一聲」，反映實際打字習慣。

### 5.4 錯誤模擬（③）
- 依 Mac 標準鍵盤的實際鍵位座標計算鍵距。
- 每一句先抽一個錯誤率 r：30% 的句子 r = 0；其餘從偏向 5–15% 的分佈抽樣，少數到 40%。
- 每一鍵依 r 決定是否出錯，錯誤類型比例為替換 50%、漏按 15%、多按 15%、對調 15%、漏聲調 5%。替換對象依鍵距加權抽樣。
- 輸出 `(打出的按鍵, 正確按鍵, 正確文字, 前文)`。

### 5.5 預訓練（④）
多任務混合，從隨機初始化開始：
- 50%：純文字下一字預測（學中文本身）。
- 50%：注音任務 `[前文][SEP][音節][OUT][文字]`，音節取自乾淨讀音或模擬錯誤後的讀音，並帶通道成本嵌入。
- 資料量：S 版約 10 億 token，M 版約 20 億 token。
- 硬體估計：單張 24 GB 消費級 GPU，S 版約 1 天，M 版約 2–3 天。這是粗估，實際以第一次訓練為準。

### 5.6 候選挖掘（⑤）—— 訓練和實際使用要一致
- 用 **ZhuyinCore 的命令列版本**（和 App 裡跑的是同一份程式碼）處理模擬按鍵，產生前 16 名候選與統計分數。
- 這樣模型看到的候選，跟使用者實際遇到的一模一樣，不會因為「訓練用 Python 模擬、上線用 Swift」而出現落差。
- 正確答案不在前 16 名時記為「召回失敗」，這代表 ①② 需要改進。排序訓練時，這類例子有一部分會補入正確答案。

### 5.7 排序微調（⑥）
- 損失 = **listwise 交叉熵**（正確候選 vs 其他候選，以序列 log 機率為分數）+ 0.2 × 語言模型損失（避免遺忘）。
- 困難負例：同音不同字、只差一個字的候選要多取樣。
- 加入「前文為空」的例子（約 20%），讓沒有前文時也能好好運作。

### 5.8 量化與匯出（⑦）
- PyTorch → coremltools，權重量化成 int8（線性層），嵌入可用 palettization。
- **一致性檢查**：開發集上量化後的首選，與 fp32 版本的一致率需 ≥ 99.5%，否則不出貨。
- 在 M1 與 M3 上量測每鍵延遲。

### 5.9 評測（⑧）
| 指標 | 條件 |
|---|---|
| 首選正確率 | 錯誤率 0% / 10% / 20% / 40% × 有前文 / 無前文 |
| 第一頁（前 9）正確率 | 同上 |
| 誤改率 | 統計首選本來就對，被模型改錯的比例（必須很低） |
| 召回率 | 正確答案在前 16 名的比例（衡量 ①②） |
| 同音詞難題集 | 人工整理的易混詞組（期中／其中、公園／公元…） |
| 口語子集 | 單獨報告 |
| 記憶效果 | 同一段文字打第二次時的首選正確率 |
| 延遲 | 逐鍵重播完整句子（含 Backspace），每鍵 P50 / P95，M1 與 M3 |
| 記憶體 | 行程實體記憶體用量 |

評測工具會**逐鍵模擬打字**，包括中途按 Backspace，而不只是把整串按鍵一次丟進去。這樣量到的是使用者真正感受到的品質和速度。

## 6. 個人記憶的演算法

| 層 | 資料結構 | 分數 |
|---|---|---|
| 精確回想 | `typedKeys → [文字]`、`cleanKeys → [文字]` | 次數與最近使用時間（半衰期 90 天）；同一組按鍵最多顯示 3 筆 |
| 讀音融合 | 讀音序列（≥ 2 音節）→ 寫法，以第一個音節建索引 | 候選句中出現相同讀音序列時替換該段，並新增為候選 |
| 語境偏好 | `(左邊的詞, 這個詞)` 的計數 | 貝氏平滑後加到 n-gram 分數上：手動選字權重 1.0、直接送出 0.3、接受補全 0.5 |
| 負面記憶 | `(讀音, 被拒的寫法)` | 送出後 5 秒內刪掉，或在候選窗略過時記錄；30 天後衰減 |

- 手動確認過 2 次以上的項目，衰減有下限，不會被完全忘記。
- 總量上限約 20,000 筆，超過時刪除分數最低的。
- 個人記憶**不經過神經網路**。它在重排之後套用，所以永遠比模型優先：你自己選過的，就是答案。

## 7. `training/` 目錄規劃

```
training/
├── SOURCES.md          語料來源與授權
├── data/               下載、清理、去重、切分腳本
├── g2p/                標音：詞庫匹配 + 多音字分類器
├── noise/              鍵盤幾何、錯誤模擬器、通道參數估計
├── lm/                 斷詞、Kneser-Ney bigram、二進位匯出
├── reranker/           模型定義、預訓練、候選挖掘、排序微調
├── export/             Core ML 匯出、量化、一致性檢查
└── eval/               逐鍵模擬評測、報表
```
