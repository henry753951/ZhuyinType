# ZhuyinType 模型與訓練設計

本文件說明容錯通道、統計語言模型、神經選字與個人記憶的設計、訓練及評測方式。以下為完整模型規劃，延遲、容量與訓練時間為設計目標或估計值；目前提供的功能見 [DESIGN.md §7](DESIGN.md#7-開發階段)。

---

## 1. 分層模型

ZhuyinType 將按鍵解讀、候選產生、語境排序與個人偏好分成四層，各層採用對應的演算法：

```
按鍵 ─► ① 容錯通道 ─► ② 詞圖 + n-gram ─► ③ 神經選字（重排）─► ④ 個人記憶 ─► 畫面
         DP，微秒級      Viterbi，毫秒級     Core ML，約 10 ms      查表，微秒級
```

| 層 | 負責 | 為什麼這樣做 |
|---|---|---|
| ① 容錯通道 | 按鍵 → 可能音節與通道成本 | 以實體鍵盤幾何與加權編輯距離計算按鍵解讀成本 |
| ② 統計 LM | 音節詞圖 → 前 16 個候選句 | 以詞頻與雙詞統計產生候選，透過召回率評估涵蓋程度 |
| ③ 神經重排 | 依前文為候選句評分 | 在固定的 16 個候選內排序，採用小型模型 |
| ④ 個人記憶 | 套用個人偏好 | 透過查表調整候選，讓已確認的寫法優先 |

**③ 的輸入包含 ① 的通道成本**，讓模型同時考量按鍵符合程度與語境分數，為精確候選與修正候選排序。

## 2. 容錯通道（KeyChannel）

### 2.1 錯誤類型
| 類型 | 例子 | 備註 |
|---|---|---|
| 替換 | 想按 `j`（ㄨ）按成 `k`（ㄜ） | 只考慮實體鍵盤上距離近的鍵，代價隨距離增加 |
| 多按 | 一次碰到兩個鍵 | 多出來的鍵如果跟前後鍵相鄰，代價較低 |
| 漏按 | 少按一鍵 | |
| 對調 | 兩鍵順序打反 | 視為一次錯誤 |
| 漏聲調 | 省略聲調後接著輸入下一個字 | 用「聲調未知」的音節表示 |

### 2.2 演算法
- 對每個「結尾鍵」，往前看 1–6 鍵的片段，跟音節表（約 1,300 個無聲調音節 × 5 個聲調）逐一算**加權受限 Damerau 編輯距離**。用帶狀 DP，片段 4 鍵以下最多容許 2 處修改，5 鍵以上最多 3 處；超過門檻就提早結束。
- 輸出每個片段的 `(音節, 通道成本, 修改次數)`。片段結果放進 LRU 快取，每鍵只需要計算新增的片段。
- 通道成本是 `-log P(按鍵 | 音節)`，由下面的參數組成：
  - `sub(d)`：依兩鍵中心距離 d 分桶（相鄰、斜對角、隔一鍵）
  - `ins_adj`、`ins_other`、`del`、`tr`、`tone_missing`

### 2.3 參數怎麼來
1. 第一版：從錯誤模擬器的設定（§5.4）直接換算。
2. 第二版：在模擬資料上對齊「真正的按鍵」和「打出的按鍵」，統計各類錯誤的發生頻率，用最大概似估計得到成本。
3. 通道與 LM 之間的權重 λ，在開發集上做格點搜尋決定。

目前的成本（自然對數）：三聲與四聲互換 5.0、二聲與輕聲互換 4.5、相鄰鍵 11、對調 9、多按或漏按 12.5。三四聲原本是 3.5，會把打對的「睡到剛剛」改成「水道剛剛」；開發集上改成 5.0 後，打對時被改錯的比例從 1.7% 降到 1.0%，按錯 10% 時的整句全對率不變（口語 54.0%、維基 45.7%），6.5 則開始變差。

### 2.4 打對的鍵優先
修正過的整句（`ScoredSentence.corrected`）必須比最好的未修正整句多 4.0 分（引擎分數加選字模型分數）才會成為首選。2.0 時，「今天ㄉㄠˇ」會被選字模型改成兩處修正的「今天的」；4.0 在打對時一樣好或更好，按錯 10% 時幾乎不變。開發集（容錯標準、加選字模型）：

| 差距 | 打對：口語 | 打對：維基 | 打對時被改錯 | 按錯 10%：口語 | 按錯 10%：維基 |
|---|---|---|---|---|---|
| 0 | 80.7% | 78.7% | 2.3%／2.0% | 58.7% | 54.0% |
| 2 | 82.7% | 79.3% | 0.3%／1.3% | 59.7% | 53.3% |
| 4 | 83.0% | 79.7% | 0.0%／1.0% | 59.7% | 53.0% |

### 2.5 模糊音
ㄗ／ㄓ、ㄘ／ㄔ、ㄙ／ㄕ、ㄣ／ㄥ、ㄢ／ㄤ 可逐項開啟（預設全關）。開啟的組合在比對時互換，每換一處成本 3.0，比三四聲互換低：開啟的人本來就分不出這兩個音，明顯更常用的詞（ㄐㄧㄥ ㄊㄧㄢ →「今天」）會勝出，同樣常用時仍以完全符合的為先。模糊音不算按錯，不占修正次數上限。全部開啟時，打對的開發集整句全對率口語 79.0% → 78.8%、維基 76.5% → 75.8%。

## 3. 統計語言模型（NGramLM）

- **斷詞**：用詞庫做最大匹配初始化，再以 unigram Viterbi 重新斷詞，重複 2 輪（硬 EM）。
- **模型**：詞級 bigram，使用 modified Kneser-Ney 平滑。依熵剪枝，控制在 30 MB 以內。
- **儲存**：log 機率量化成 8 bit，存成雜湊表二進位檔，啟動時直接透過 mmap 讀取。
- **詞庫**：每個詞記錄所有讀音，以台灣標準讀音為主。「一」「不」另外收變調後的讀音，因為很多人照實際發音打：詞裡的「一」在四聲與輕聲前收 ㄧˊ、其他聲調前收 ㄧˋ（一定 ㄧˊ ㄉㄧㄥˋ、一直 ㄧˋ ㄓˊ），「不」在四聲前收 ㄅㄨˊ（不要 ㄅㄨˊ ㄧㄠˋ）；單獨的「一」「不」打變調時扣 2.5 分。
- **讀音機率**：詞庫的分數是 log P(詞, 讀音)。多音字依 Unihan kHanyuPinlu 的讀音次數分配字頻（加一平滑），所以「說」打 ㄕㄨㄛ 時分數不變，打 ㄕㄨㄟˋ 時低 9 分，「睡」就排在前面。CC-CEDICT 標成整筆台灣讀音的（「微」/Taiwan pr. [wei2]/）承接大陸讀音的次數；只寫在某個義項裡的（「和」當連詞時的 ㄏㄢˋ、「行」的品行義）不改變主要讀音，但至少分到該字頻率的 25%，因為 kHanyuPinlu 統計的是大陸用法，台灣讀音的次數在裡面是零。引擎讀詞庫時把分數拆成詞的機率（取最常見讀音的分數）和讀音的相對機率，後者加在語言模型分數上：分數 = log P(詞 | 前文) + log P(讀音 | 詞)。同一個詞同時以完全符合與聲調容錯對上時，取扣分後較高的那個，所以「吧」打成 ㄅㄚ 時用 ㄅㄚ˙ 的分數。開發集（同樣以新詞庫的讀音打字、加選字模型）：口語 79.0% → 80.8%、維基 77.2% → 78.8%；測試集：維基 77.8% → 80.2%、口語 78.8% → 80.0%、日常短句 98.5% → 100%。

## 4. 神經選字模型（Reranker）

### 目前的實作（v2b，0.2.4 起）
- **模型**：字級因果 Transformer 語言模型，8 層、寬 512、8 個注意力頭、FFN 2048，含嵌入約 3,100 萬參數，上下文 64 字，字表 12,000 字（與 v1 相同）。字表以外的字共用 <unk>，計分時每個字只分到 1/5,465。
- **訓練**：`training/reranker/`。維基百科 2,011 萬句加上台灣口語 600 萬句（口語重複兩次），共約 9.6 億字；和測試集、開發集有 8 字重疊的句子全部排除。H100（MIG 3g.47gb）上 90,000 步約 79 分鐘；開發集困惑度（每字）：維基 23.4、口語 65.1（v1：29.6、75.3）。實驗紀錄見 `training/reranker/REPORT_v2.md`。
- **推論**：`Sources/ZhuyinML`。Core ML（fp16，約 60 MB），引擎的前 16 個整句一次送入，模型直接輸出每個字的對數機率。最終分數 = 引擎分數 + 1.0 × 模型分數，權重與句數以開發集選定。前文見下面「游標前的文字」。
- **運算單元**：只用 CPU。打一句 25 個音節的句子時，每次 4–21 ms（v1 是 2–11 ms）；GPU 每次約 30 ms（多半是派送成本），第一次還要約 130 ms 暖機；神經引擎與 CPU 相近。
- **候選窗**：打開候選窗時，每個長度的前 24 個候選也加上 1.0 × 模型分數重新排序（前文 = 游標前的文字 + 這段組字中它前面的字），每個長度一次呼叫。例如沒有前文時 ㄕˋ 先列出「是」（原本是「事」），「這」之後的 ㄍㄜˋ 先列出「個」（原本是「鉻」）。
- **成績**（測試集，容錯標準，0.2.3 引擎）：

| 選字模型 | 維基 | 口語 | 日常短句 | 維基（有前文） | 口語（有前文） |
|---|---|---|---|---|---|
| 無（只用引擎，0.1） | 65.5% | 71.0% | | | |
| v1 | 80.5% | 80.5% | 100% | 83.0% | 80.8% |
| v2b | 80.8% | 82.8% | 100% | 85.2% | 83.0% |

### 游標前的文字
組字開始時向 App 讀取游標前最多 32 個字（`IMKTextInput` 的 `selectedRange` 與 `attributedSubstring`）：選字模型以它為前文，引擎從它最後一段中文的最後兩個詞接著算（從尾端以詞庫最長比對切詞；結尾是空白、標點或換行時當作句首）。App 不提供時，改用同一個 App 在 10 分鐘內送出的字；空白、Return、Backspace 會跟著更新，點擊或方向鍵只讓引擎回到句首，選字模型仍參考這段文字，直到重新讀到 App 的文字或超過 10 分鐘。這段文字只在記憶體中，不寫入磁碟，可在設定關閉。

評測（`conversion_eval.py --line-context`，每段以同一行前面的文字為前文；口語集多半一行一句，影響小）：

| | 維基開發集 | 維基測試集 | 口語測試集 |
|---|---|---|---|
| 沒有前文 | 80.3% | 80.8% | 80.5% |
| 有前文 | 84.2% | 83.2% | 80.8% |

前文下把選字模型權重提高到 1.4 反而變差（開發集 83.3%），維持 1.0。

### 候選字清單
- 預設只列照實際按鍵對得上的字詞：第一項是目前顯示的文字，接著是較長的詞，最後是單字；只列詞庫裡的詞與單字，不列把轉換結果切下來拼成的片段（如「漢選」）。
- Shift-↑ 切換到修正清單（按錯修正與模糊音的候選在前，其後是照按鍵的字詞），再按一次還原；視窗下方的「⇧↑ 修正」也可以點。很多 App 把 Option 組合鍵當自己的快捷鍵，所以清單不用 Option。
- Shift-↓ 只列游標處的單字。
- 每個長度的前 24 個候選依前文由選字模型重新排序。選字模型字表以外的字（詞庫裡有 5,465 個）共用一個 <unk>，每個字只分到 <unk> 機率的 1/5,465（減 log 5465 ≈ 8.6），罕用字才不會排到常用字前面。

### 接續已送出的字
組字原本一律當成句首（`<s>`）。現在一段組字送出後，下一段的語言模型歷史接在剛送出的詞後面；送出的最後一個是標點或符號、有鍵傳給 App，或主程式呼叫 `breakContext()` 時，才回到句首。評測：每句從中間的詞界切成兩次送出（`conversion_eval.py --split`），開發集整句全對率：

| | 口語 | 維基 |
|---|---|---|
| 只用引擎，每段當句首 | 65.0% | 62.3% |
| 只用引擎，接續 | 69.0% | 65.2% |
| 加上選字模型，每段當句首 | 77.0% | 72.8% |
| 加上選字模型，接續 | 77.0% | 74.0% |

### 試過但沒採用
- **快照三元模型（`data/build/lm2`）+ 選字模型**：開發集較好（口語 83.5%、維基 79.0%），但測試集沒有（維基 76.2%、口語 79.2%、日常短句 95.6%，原本 76.8%、79.0%、98.5%），維持二元模型。

以下為規劃中的完整版（以讀音與通道成本為輸入、以排序目標微調）。

### 4.1 輸入格式
```
[BOS] 前文字元 ×≤64  [SEP]  音節 ×n  [OUT]  候選字 c1 … cn
```
- **前文**：游標前、已確認的文字（最多 64 字）。遇到 Secure Input 時是空的。
- **音節 token** = 聲母韻母組合嵌入 + 聲調嵌入 + **通道成本嵌入**（成本分成 0／1／2／3+ 四桶）+ **修正類型嵌入**（無／替換／多按／漏按／對調／缺聲調）。
- **輸出**：`log P(候選 | 前文, 音節)` = Σ log P(cᵢ | 前文, 音節, c<ᵢ)。
- 候選字數必須等於音節數（一個音節對一個字）。

### 4.2 架構
Decoder-only Transformer，從零訓練：RoPE 位置編碼、RMSNorm、SwiGLU，輸入與輸出嵌入共用權重。

| 版本 | 層 × 寬度 × 頭數 | FFN | 字表 | 參數量 | int8 大小 | 用途 |
|---|---|---|---|---|---|---|
| S | 6 × 384 × 6 | 1024 | 約 20k | 約 15M | 約 15 MB | 預設版本，以 M1 為效能評測基準 |
| M | 8 × 512 × 8 | 1536 | 約 20k | 約 32M | 約 32 MB | 較大容量的選用版本 |

### 4.3 推論加速
- **前綴樹批次**：16 個候選常常前面幾個字相同。把它們排成一棵樹，用「只看祖先」的 attention mask 一次算完；結果跟逐一計算相同。
- **前文 KV 快取**：同一段組字共用固定前文，計算一次後重複使用。macOS 15 以上採 Core ML stateful model；macOS 14 每次重算前文，以 40 ms 為推論時限目標。
- **時限**：先顯示統計結果，神經結果依 40 ms 時限與請求序號套用；逾時結果只有在請求序號仍有效時才更新畫面。

### 4.4 與統計分數融合
```
最終分數 = 統計分數 + w × 模型分數
只有當某候選的最終分數超過統計首選 τ 以上，才換掉首選。
```
w 與 τ 在開發集上校準，以保留正確的統計首選為優先；同時量測首選正確率與誤改率，決定更新首選的門檻。

## 5. 訓練流程

```
語料 ─► ① 清理 ─► ② 標音 ─► ③ 錯誤模擬 ─► ④ 預訓練 ─► ⑤ 用真引擎產生候選 ─► ⑥ 排序微調 ─► ⑦ 量化匯出 ─► ⑧ 評測
```

### 5.1 語料（只用允許再散布模型權重的來源）

| 類別 | 候選來源 | 授權（使用前逐一確認） |
|---|---|---|
| 百科 | 中文維基百科（轉台灣正體）、維基文庫 | CC BY-SA |
| 網頁 | 以 CC0 或 ODC-By 釋出的大型網頁語料（繁體子集） | CC0 / ODC-By |
| 政府 | 政府資料開放平臺的新聞稿、公報等文字 | 政府資料開放授權條款第 1 版 |
| 口語 | 群眾募集語音計畫的 zh-TW 朗讀句子 | CC0 |

- **資料納入條件**：來源可追溯、具明確商用與模型權重再散布授權的原始文字。
- **資料涵蓋**：口語、網路用語偏少。訓練時提高口語句子與個人記憶的權重，評測時單獨列出口語分數。
- 所有來源記錄在 `training/SOURCES.md`；模型權重的授權依實際使用的資料決定（若含 CC BY-SA 資料，權重也以 CC BY-SA 釋出）。

### 5.2 清理與切分（①）
1. 轉成台灣正體；能取得原生繁體的來源就優先用。
2. 依句末標點切句，保留 4–64 字的句子；去除網址、程式碼、非中文比例過高的句子。
3. 用 MinHash 去重。
4. **訓練開始前**先切出測試集（依來源、句長分層，約 5,000 句），再刪除訓練資料中與測試句有連續 8 字相同的句子。各版本沿用固定測試集進行比較。

### 5.3 標音（②）
- 先用詞庫做最長匹配，詞的讀音優先於單字讀音。
- 多音字（了、著、行、長、得、重……）：訓練小型分類器（字 + 左右各 4 字 → 讀音），以詞庫中讀音明確的句子作為訓練資料。
- 標音信心低的句子用於預訓練的純文字任務；排序微調採用標音信心達到門檻的句子。
- 輕聲字：語尾助詞同時接受「輕聲」和「一聲」，反映實際打字習慣。

### 5.4 錯誤模擬（③）
- 依 Mac 標準鍵盤的實際鍵位座標計算鍵距。
- 每一句先抽一個錯誤率 r：30% 的句子 r = 0；其餘從偏向 5–15% 的分佈抽樣，少數到 40%。
- 每一鍵依 r 決定是否出錯，錯誤類型比例為替換 50%、漏按 15%、多按 15%、對調 15%、漏聲調 5%。替換對象依鍵距加權抽樣。
- 輸出 `(打出的按鍵, 正確按鍵, 正確文字, 前文)`。

### 5.5 預訓練（④）
多任務混合，從隨機初始化開始：
- 50%：純文字下一字預測（學中文本身）。
- 50%：注音任務 `[前文][SEP][音節][OUT][文字]`，音節取自乾淨讀音或模擬錯誤後的讀音，並帶通道成本嵌入。
- 資料量：S 版約 10 億 token，M 版約 20 億 token。
- 硬體估計：單張 24 GB 消費級 GPU，S 版約 1 天，M 版約 2–3 天。這是粗估，實際以第一次訓練為準。

### 5.6 候選挖掘（⑤）
- 用 **ZhuyinCore 的命令列版本**（和 App 裡跑的是同一份程式碼）處理模擬按鍵，產生前 16 名候選與統計分數。
- 訓練與執行階段共用 Swift 引擎，使用相同的候選產生流程。
- 正確答案在前 16 名以外時記為「召回失敗」，作為調整 ①② 的依據。排序訓練時，這類例子有一部分會補入正確答案。

### 5.7 排序微調（⑥）
- 損失 = **listwise 交叉熵**（正確候選與其餘候選，以序列 log 機率為分數）+ 0.2 × 語言模型損失（維持語言建模能力）。
- 困難負例：同音不同字、只差一個字的候選要多取樣。
- 加入「前文為空」的例子（約 20%），涵蓋僅依注音排序的情境。

### 5.8 量化與匯出（⑦）
- PyTorch → coremltools，權重量化成 int8（線性層），嵌入可用 palettization。
- **一致性檢查**：開發集上量化後的首選與 fp32 版本的一致率達 ≥ 99.5%，才達到發布標準。
- 在 M1 與 M3 上量測每鍵延遲。

### 5.9 評測（⑧）
| 指標 | 條件 |
|---|---|
| 首選正確率 | 錯誤率 0% / 10% / 20% / 40% × 有前文 / 無前文 |
| 第一頁（前 9）正確率 | 同上 |
| 誤改率 | 統計首選本來就對，被模型改錯的比例（必須很低） |
| 召回率 | 正確答案在前 16 名的比例（衡量 ①②） |
| 同音詞難題集 | 人工整理的易混詞組（期中／其中、公園／公元……） |
| 口語子集 | 單獨報告 |
| 記憶效果 | 同一段文字打第二次時的首選正確率 |
| 延遲 | 逐鍵重播完整句子（含 Backspace），每鍵 P50 / P95，M1 與 M3 |
| 記憶體 | 行程實體記憶體用量 |

評測工具會**逐鍵模擬打字**，包括中途按 Backspace，量測完整輸入過程的候選品質與延遲。

## 6. 個人語言模型

個人記憶是一個會隨使用調整的 n-gram 模型，和基礎模型動態混合，記住的內容自然只在相同的上下文生效。

### 6.1 計數
每次送出時，把最終的詞序列加進個人的一、二、三連詞計數。手動選過的部分權重高，直接接受的部分權重低；手動選過的多詞片語另外以實際按鍵的讀音存成一個個人詞，讓詞庫沒有的說法也能成為候選。

### 6.2 短期與長期
| | 短期 | 長期 |
|---|---|---|
| 用途 | 這幾天的人名、話題、對話用詞 | 長久的用字習慣 |
| 半衰期 | 8 小時 | 90 天 |
| 進入方式 | 每次送出 | 手動選字直接進入；其他在兩個不同日子使用後升級 |
| 累積 | 每次 | 每個 n-gram 一天最多加一次（手動選字除外） |
| 保底 | 無 | 手動選過 3 次以上不會消失 |

### 6.3 混合
```
P(詞 | 前文) = (1 − λ) × P基礎(詞 | 前文) + λ × P個人(詞 | 前文)
λ = C(前文) / (C(前文) + κ)
```
λ 由這個前文在個人記錄裡的份量決定，前文越短，κ 越大，所以一次觀察只在完整的上下文明顯生效，要在多種情境反覆出現才會推廣。在相同上下文改選別的詞時，舊的計數減半，最新的選擇優先。自訂詞永遠排在個人記憶之前。

### 6.4 送出後刪掉重打
送出後 30 秒內，用 Backspace 從尾端整個刪掉某些詞，接著打同樣的讀音、送出不同的字，就當成改字：新的字以手動選字的權重學習，刪掉的字在原本的前文裡減半。刪除時，下一段組字的前文改成還留著的詞。每次送出時，前一次送出的最後兩個詞也一起成為個人 n-gram 的前文，所以分兩次送出的句子也學得到跨越兩段的接續。

### 6.5 不記住的字詞、匯出與匯入
「記住的字詞」可以把選取的詞設為不記住：馬上忘掉，之後送出也不學；這些詞仍列在清單裡，移除後恢復學習。匯出把自訂詞、記住的字詞、個人 n-gram 和不記住的清單存成一個文字檔；匯入時加到現有資料，兩邊都有的項目保留較強的那一筆。

### 6.6 用模擬使用者校準
w_pick、w_passive 與各階 κ 不靠手調：從口語語料建立許多模擬使用者，讓他們逐鍵打字、在結果不對時改字，再量三件事——
1. 改過一次的說法，下次出現時的正確率；
2. 從未出現過的句子，正確率相對於空白記憶有沒有下降；
3. 單一觀察會不會擴散到其他上下文（例如「你嗎」問句）。

### 6.7 研究方向：把記憶交給神經選字模型
神經選字模型（§4）除了前文、讀音與候選句，也接收個人訊號作為輸入：個人模型分數、這段是否曾被手動改過、距離上次使用多久、目前所在的 App。模型自行學會什麼情況下該相信記憶。訓練資料同樣由模擬使用者產生：每個模擬使用者有自己的慣用說法與改字紀錄，模型學習在他們的歷史下挑出正確的整句。
