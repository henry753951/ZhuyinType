### 2.2 同音字：在／再（0.4.0 完成）

在、再都念 ㄗㄞˋ，選錯很刺眼。最常錯的是句首（「再等我五分鐘」）與「在／再＋動詞」（我在吃／我再吃一碗）。

資料放在 `ml/src/zhuyintype_ml/training/homophone/`。從維基百科、口語語料與真實口語文字挖出含在、再的句子，依位置分成詞內、代名詞後、句首、動詞前、地點時間前與其他。開發與測試集各約 1,000 句，在、再各半。標籤由規則與語言模型雙重確認，再經人工抽查。其他 25 組常見同音字也用同樣的方法建立，例如做／作、已／以、他／她／它、像／向／象。

模型從 v3 繼續訓練音節對字編碼器。含在／再的批次提高取樣，其中一半是句首，這些位置的損失乘 3。訓練只用可以隨 app 發布的來源；第一輪含 Taiwan Tongues，所以不採用。

結果（app 設定）：

| 項目 | 沒有前文 | 有前文 |
|---|---|---|
| 在／再測試集，微調前 | 87.4% | 92.2% |
| 在／再測試集，微調後 | 91.5% | 94.7% |
| 改對／改壞 | 43／0 | 26／0 |
| 句首的再，微調前 | 48% | 76% |
| 句首的再，微調後 | 70% | 86% |

一般開發集的差異在雜訊範圍內：口語 87.0% 與 87.0%，維基有前文從 83.8% 到 84.0%，Taiwan Tongues 從 71.3% 到 70.8%。其他 25 組同音字提高 0.3 分。

還沒解決的問題：沒有前文時，「再試試看」仍是「在試試看」。原因在引擎的句首機率，P(在) 遠高於 P(再)，模型雖然偏向「再」，但不足以改變結果。這一項列入 0.5 的排名微調（[research/plan.md](research/plan.md) B1）。

### 2.3 跨平台核心與遠端評測

之後要做 Linux 與 Windows 輸入法，共用同一個引擎與模型。評測也要搬到 GPU 主機（64 核心）上跑。

原則是依平台各自優化。跨平台共用的只有引擎邏輯（Rust，`engine/`）與訓練好的權重，每個平台用最適合的執行方式與介面。macOS 是主要平台，維持專門的優化，不經過任何跨平台層：

- Core ML（CPU／神經引擎，之後加上有狀態的前文模型與 int8 權重）
- InputMethodKit
- 原生介面

| 平台 | 引擎 | 模型執行 | 輸入法介面 |
|---|---|---|---|
| macOS | Rust 引擎，經由 C ABI | Core ML（由 App 執行，引擎回呼） | InputMethodKit（現有 app） |
| Linux | Rust 引擎 | ONNX Runtime（CPU；需要時 CUDA／OpenVINO） | fcitx5 或 IBus，經由 C ABI 呼叫引擎 |
| Windows | Rust 引擎 | ONNX Runtime（DirectML 或 CPU） | TSF，經由 C ABI 呼叫引擎 |

做法：

- 引擎移植到 Rust（2026-10 完成，和 Swift 版逐位元相同）：zhuyin-cli 在 Linux 上以 ONNX Runtime 執行模型，C ABI（`zhuyin-ffi`）供各平台的輸入法使用，macOS App 已改用它。
- 模型另外匯出 ONNX，引擎透過 ONNX Runtime C API 呼叫。模型呼叫的介面保持精簡，讓每個平台分別調校。
- 所有評測工具與參數掃描在遠端以全部核心執行。
- 各平台的打包方式寫成計畫（`ml/src/zhuyintype_ml/remote/PORTING.md`）；引擎的 C ABI 見 `engine/DESIGN.md` §6。

完成標準：

- 同一組評測在 Mac 與遠端的輸出，不同的行數不超過 1%。
- macOS 的建置、行為與速度不變。
- 整組參數掃描比 Mac 明顯快。

目前狀態：遠端評測已完成（`ml/src/zhuyintype_ml/remote/`），四種評測工具與參數掃描都能用全部核心執行（當時以 Swift 引擎驗證：Mac 花 1,174 秒，遠端 CPU 610 秒，遠端 GPU 393 秒，輸出差異 10／6,000 行）。引擎已移植到 Rust，GPU 主機以 Rust 的 zhuyin-cli 與 ONNX Runtime 1.24.4 評測；C ABI（`zhuyin-ffi`）已完成，macOS App 改用它。Linux／Windows 的輸入法介面還沒開始，計畫在 `ml/src/zhuyintype_ml/remote/PORTING.md`。

## 3. 0.5–0.7 規劃：免選字、補標點、補全

架構原則：多層、可拆、分別訓練再融合。每一層（按鍵解碼、容錯通道、聊天／百科語言模型與個人 n-gram、v3 逐字模型、整句重排、補全）有固定的介面，可以單獨訓練、單獨替換、放進模型目錄熱載入，最後在同一張詞圖、同一個對數尺度上融合。

| 版本 | 項目 | 做法 | 驗收 |
|---|---|---|---|
| 0.5.0 | 學習式融合 | 用開發集的前 16 句，以各層分數為特徵訓練小的融合模型，取代手調權重，並輸出整句信心 | 整句全對率高於手調權重 |
| 0.5.0 | 免選字指標 | 一句話從頭打到尾完全不選字的比例，作為主要指標，每版報告 | 每版提升，選字改壞其他字不增加 |
| 0.5.0 | 補標點 | 在 v3 雙向音節編碼器上加標點頭，不另外載入模型。字之間與句尾都補（例如「嗎」後的「？」），只在有把握時補。按 Enter 送出時套用 | F1 > 0.82、precision ≥ 0.90，支援句尾 |
| 0.6.0 | 補全建議與 Tab | v3 前文編碼器（逐字語言模型）沿詞庫字典樹與個人片語展開，只提示機率夠高的詞，例如「晚上想吃麻」提示「辣鍋」，再打「婆」後提示「豆腐」。提示以灰字顯示，按 Tab 接受，直接打下去就忽略。聊天／百科比例同樣套用 | 提示出現時正確率 ≥ 90%，量每句平均省下的按鍵數，打錯一鍵時提示仍正確 |
| 0.7.0 | 不打聲調（選用） | v3 訓練加入「聲調未知」，詞圖用不帶聲調的比對 | RIME 50 句整句 ≥ 90%；打聲調時結果不變 |
| 0.7.0 | Linux／Windows | 引擎 C 介面，接 fcitx5／IBus 與 TSF；各平台用最適合的模型執行方式 | 三個平台的評測結果一致 |

| 11 | Linux／Windows 輸入法 | 共用引擎與模型 | 依 §2.3 的順序，先做 C ABI，再接 fcitx5／IBus，最後是 Windows TSF | 各平台能完成基本輸入與選字 |
| 12 | 簽署與公證 | 目前是 ad-hoc 簽章 | Developer ID 簽署、公證、universal binary | 下載後不出現安全性提示 |
| 13 | 專有名詞與網路用語 | 店名、人名、網路用語、IT 詞彙的整句全對率只有 25–54%（[比較](benchmarks/competition.md#專有名詞與網路用語)） | 從授權可用的來源建立可選用的詞包（人名、地名與店名、網路用語、IT、ACG），詞包內的詞以個人詞的方式加分；研究善解的詞包做法，自行實作 | 這些集合提升 30 個百分點以上，一般開發集不降 |
| 14 | 部件查字 | 完全不知道讀音的字（罕見姓氏、地名、文件上看到的字）用讀音打不出來 | 讀音變體、口語語氣詞與誤讀評測集完成後才做。在 App 這一層實作：按快捷鍵進入（可在設定中關閉），用注音打出部件，例如「虫」「可」，從結果中選字，直接插入組字中。不記住當時打的讀音。拆解資料用 BabelStone IDS 與 Unihan | 能打出常用字表與罕用字表中所有拆得出部件的字；關閉時不影響一般輸入與延遲 |

研究方向：把個人訊號（個人模型分數、是否改過、距離上次使用多久、目前的 App）當成神經模型的輸入，讓模型自己學什麼時候該相信記憶。
