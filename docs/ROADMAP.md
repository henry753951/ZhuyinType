### 2.2 同音字：在／再
- **為什麼**：在、再都念 ㄗㄞˋ，選錯很刺眼。目前整句重排已經能處理大部分，句首（「再試試看」）與「在／再 + 動詞」（我在吃／我再吃一碗）仍會錯。
- **怎麼做**（`training/homophone/`）：
  1. 從維基百科、口語語料與 Taiwan Tongues 挖出含在、再的句子，依位置分類（詞內、代名詞後、句首、動詞前、地點時間前、其他）。
  2. 開發與測試集各約 1,000 句，在／再大致各半，每個標籤由規則與語言模型雙重確認，人工抽查 100 句。
  3. 同一套方法延伸到其他常見同音字（做／作、已／以、他／她／它、像／向／象……）。
  4. 微調 v3 音節對字編碼器：含這些字的段落提高取樣比例、這些位置的損失加重；必要時同樣微調 v2b。
- **狀態**：第一次挖掘的程式有 bug（找到 0 句），正在修正後重跑；之後在 GPU 主機上訓練與評測，驗收後發布 0.3.1。目前單獨打 ㄗㄞˋ ㄧ ㄘˋ 仍是「在一次」，「再試試看」「再等我五分鐘」在句首也會選錯。
- **完成標準**：在／再開發集每一類都提高；一般開發集不下降（v3 每個位置的首選正確率不低於原本 0.2 點以上）；最後跑一次測試集與短句集。

### 2.3 跨平台核心與遠端評測
- **為什麼**：之後要做 Linux 與 Windows 輸入法，共用同一個引擎與模型；評測也要搬到 GPU 主機（64 核心）上跑。
- **原則：依平台各自優化。** 跨平台共用的只有引擎邏輯（ZhuyinCore，純 Swift）與訓練好的權重；每個平台用最適合的執行方式與介面。macOS 是主要平台，維持專門的優化：Core ML（CPU／神經引擎，之後的有狀態前文模型與 int8 權重）、InputMethodKit、原生介面，不經過任何跨平台層。

| 平台 | 引擎 | 模型執行 | 輸入法介面 |
|---|---|---|---|
| macOS | ZhuyinCore | Core ML | InputMethodKit（現有 app） |
| Linux | ZhuyinCore（Swift for Linux） | ONNX Runtime（CPU；需要時 CUDA／OpenVINO） | fcitx5 或 IBus，經由 C ABI 呼叫引擎 |
| Windows | ZhuyinCore（Swift for Windows） | ONNX Runtime（DirectML 或 CPU） | TSF，經由 C ABI 呼叫引擎 |

- **怎麼做**：ZhuyinCore 與 zhuyin-cli 在 Linux 編譯；模型另外匯出 ONNX，Swift 透過 ONNX Runtime C API 呼叫，模型呼叫的介面保持精簡，讓每個平台分別調校；所有評測工具與參數掃描在遠端以全部核心執行；引擎的 C ABI 與各平台打包方式寫成計畫（`training/remote_eval/PORTING.md`）。
- **完成標準**：同一組評測在 Mac 與遠端的輸出不同的行數不超過 1%；macOS 的建置、行為與速度不變；整組參數掃描比 Mac 明顯快。
- **狀態**：遠端評測完成（`training/remote_eval/`）：Swift 6.4.1 與 ONNX Runtime 1.24.4 裝在 GPU 主機上，四種評測工具與參數掃描都能用全部核心執行；驗證時 Mac 1,174 秒、遠端 CPU 610 秒、遠端 GPU 393 秒，輸出差異 10／6,000 行。引擎的 C ABI 與 Linux／Windows 輸入法介面還沒開始，計畫在 `training/remote_eval/PORTING.md`。

## 3. 0.5–0.7 規劃：免選字、補標點、補全

架構原則：多層、可拆、分別訓練再融合。每一層（按鍵解碼、容錯通道、聊天／百科語言模型與個人 n-gram、v3 逐字模型、整句重排、補全）有固定的介面，可以單獨訓練、單獨替換、放進模型目錄熱載入，最後在同一張詞圖、同一個對數尺度上融合。

| 版本 | 項目 | 做法 | 驗收 |
|---|---|---|---|
| 0.5.0 | 學習式融合 | 用開發集的前 16 句，以各層分數為特徵訓練小的融合模型，取代手調權重，並輸出整句信心 | 整句全對率高於手調權重 |
| 0.5.0 | 免選字指標 | 一句話從頭打到尾完全不選字的比例，作為主要指標；對打評測（同句、同注音輸入）比較 | 高於對照組 |
| 0.5.0 | 補標點 | 在 v3 雙向音節編碼器上加標點頭（不另外載入模型），字之間與句尾（「嗎」後的「？」）都補，只在有把握時補；按 Enter 送出時套用 | F1 > 0.82、precision ≥ 0.90，支援句尾 |
| 0.5.0 | 隱私欄位 | 密碼與私人欄位不讀前文、不學習、不送模型 | 檢查涵蓋 |
| 0.6.0 | 補全建議與 Tab | v3 前文編碼器（逐字語言模型）沿詞庫字典樹與個人片語展開，只提示機率夠高的詞（「晚上想吃麻」→「辣鍋」，打「婆」後→「豆腐」）；灰字顯示，Tab 接受，直接打下去就忽略；聊天／百科比例同樣套用 | 提示出現時正確率 ≥ 90%；量每句平均省下的按鍵數；打錯一鍵時提示仍正確 |
| 0.7.0 | 不打聲調（選用） | v3 訓練加入「聲調未知」，詞圖用不帶聲調的比對 | 同一組句子的整句全對率高於對照組 |
| 0.7.0 | Linux／Windows | 引擎 C 介面，接 fcitx5／IBus 與 TSF；各平台用最適合的模型執行方式 | 三個平台的評測結果一致 |

## 4. 接下來（0.4.0 之前）

依建議的順序排列。

| # | 工作 | 為什麼 | 怎麼做 | 完成標準 |
|---|---|---|---|---|
| 1 | 降低每鍵延遲 | 0.3.0 長句每鍵 p95 53 ms，超過 30 ms 目標；時間主要在整句重排 | 16 個候選共用的前綴只算一次（前綴樹批次或 KV 快取）、句子越長越少送幾句、v3 前文編碼結果跨組字重用；量 p95 與能耗 | 25 個音節 p95 < 30 ms，準確率不降 |
| 2 | 「台／臺」等寫法偏好 | 模型從維基學到「臺」，日常多寫「台」；Taiwan Tongues 開發集只差寫法的句子占 15 個百分點 | 輸出前依偏好統一寫法（預設「台」），候選字清單去掉重複；選了另一種寫法就記住 | 「視為相同」與原始整句全對率的差距接近 0 |
| 3 | v3 讀更長的前文 | App 只讀 32 字，v3 能用 255 字 | 讀取上限提高到 64–128 字，分別量準確率與延遲 | 維基（有前文）提高，組字開始的延遲 p95 < 30 ms |
| 4 | v3 的邊界輸入 | v3 訓練時有 20% 一聲省略空白，但 app 一律送「明確邊界」 | 把 KeyDecoder 的隱含邊界帶進 token，傳給 v3 | 一聲省略空白的整句全對率提高 |
| 5 | v3 用在候選字清單 | 清單現在只用 v2b 排序 | 用 v3 每個位置的字機率排序單字與詞 | 候選字清單第一頁命中率提高 |
| 6 | 模型大小與延遲 | v3 129 MB、v2b 60 MB；前文編碼器 256 字約 23 ms | int8 量化或 palettization；macOS 15 以上用有狀態模型保存前文；若 v3 夠好，評估拿掉 v2b | 大小減半、準確率不降 |
| 7 | 核心檢查的延遲門檻 | 機器忙的時候，40 音節「輕聲容錯」單鍵最慢 3–4 ms，超過 3 ms 門檻 | 先在空閒時重量；仍超過就找出慢的步驟 | `make checks` 全部通過 |
| 8 | 真正的聊天語料 | 聊天模型的語料多半是產生的句子與朗讀句，困惑度比百科模型還高 | 尋找授權允許再散布的對話文字；多輪對話生成讓每句都有前文 | 聊天開發集的困惑度低於百科模型 |
| 9 | 個人模型校準 | 個人模型的權重與 κ 是手設的 | 用模擬使用者逐鍵打字、改字，量改過的說法下次的正確率、沒出現過的句子有沒有變差、會不會擴散到別的上下文 | 三項指標都有數字，選出參數 |
| 10 | Linux／Windows 輸入法 | 共用引擎與模型 | 依 §2.3 的計畫：先 C ABI，再 fcitx5／IBus，最後 Windows TSF | 各平台能完成基本輸入與選字 |
| 11 | P5 功能 | — | 中英混打、Emoji、符號表、繁簡輸出、倚天與許氏鍵盤排列、使用者啟動的更新檢查、Secure Input 時暫停學習與前文 | 各自的檢查 |
| 12 | 發布 | 目前是 ad-hoc 簽章、只有建置機的架構 | Developer ID 簽署、公證、universal binary | 下載後不出現安全性提示 |

研究方向：把個人訊號（個人模型分數、是否改過、距離上次使用多久、目前的 App）當成神經模型的輸入，讓模型自己學什麼時候該相信記憶。
