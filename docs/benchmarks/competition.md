# 與其他注音輸入法的比較

這一頁把 ZhuyinType 和兩個公開研究過程的注音輸入法——靈犀注音（0c）與善解（shanjie）——放在同一批句子、同一批按鍵上比較。目的是看清楚各自的取捨與我們自己的不足，不是排名。三個專案的設計目標不同，一個數字不能代表一個輸入法的好壞；各專案的做法與我們從中學到的，見 [相關工作](../research/related-work.md)。

量測日期：2026-10-28。這一頁由紀錄檔產生（`zt bench compare --render`），不手動修改。

## 摘要

- ZhuyinType 建立的 9 組句子（沒有前文，V）：ZhuyinType 為 75.8–100.0%。和靈犀（統計）相比，ZhuyinType 顯著較高的 4 組、差異不顯著的 5 組；和靈犀（完整）相比，ZhuyinType 顯著較高的 4 組、差異不顯著的 5 組；和善解（聊天）相比，ZhuyinType 顯著較高的 9 組；和善解（正式）相比，ZhuyinType 顯著較高的 7 組、差異不顯著的 2 組。
- 善解建立的 35 組句子（S）：和善解（聊天）相比，ZhuyinType 顯著較高的 4 組、善解（聊天）顯著較高的 11 組、差異不顯著的 20 組。善解（聊天）較高、差距最大的是店名 26.7% 對 88.4%（p < 0.001）、網路用語（第二輪） 30.5% 對 86.0%（p < 0.001）、IT 詞彙 26.7% 對 76.7%（p < 0.001）。ZhuyinType 較高、差距最大的是使用者回報的錯誤句（開發） 65.2% 對 35.4%（p < 0.001）、使用者回報的錯誤句 70.0% 對 41.2%（p < 0.001）、保留集：對話 86.7% 對 76.7%（p 0.003）。
- 善解建立的 35 組句子（S）：和善解（正式）相比，ZhuyinType 顯著較高的 3 組、善解（正式）顯著較高的 11 組、差異不顯著的 21 組。善解（正式）較高、差距最大的是網路用語（第二輪） 30.5% 對 72.5%（p < 0.001）、IT 詞彙 26.7% 對 65.0%（p < 0.001）、店名 26.7% 對 64.4%（p < 0.001）。ZhuyinType 較高、差距最大的是使用者回報的錯誤句 70.0% 對 35.0%（p < 0.001）、使用者回報的錯誤句（開發） 65.2% 對 31.1%（p < 0.001）、虛詞（fw） 95.2% 對 88.7%（p 0.004）。
- 靈犀注音公開的 115 個回歸案例（V）：ZhuyinType 85.2%、只用引擎 78.3%、靈犀（統計） 86.1%、靈犀（完整） 85.2%、善解（聊天） 83.5%、善解（正式） 79.1%。

## 比較的對象與設定

|  | 版本 | 設定 |
|---|---|---|
| ZhuyinType | 引擎 commit `399c95e`，App 版本號 0.4.1 | 和 App 相同：`--config app`（`zhuyin-cli --models`）。另列「只用引擎」：只有詞庫與語言模型（`--config engine`） |
| 靈犀注音（0c） | commit `3fb0917`，v0.2.6 發布的詞庫與模型 | 統計引擎；完整設定（加上 D512 選字模型，預設 100 ms 時限，每個程序一個推論執行緒）。標準鍵盤，混打、補標點、不打聲調關閉 |
| 善解（shanjie） | commit `bd3b609`，發布的模型與詞包（ACG、IT） | 聊天配置（含口語項）；正式配置。小模型重排開啟（標準強度）。讀音經由它的評測程式 `shanjie-eval`；含打錯的按鍵經由它 App 使用的 C 介面，以未修改的原始碼建成共享程式庫（cdylib）呼叫 |

- 所有系統都在同一台主機（Linux x86_64, 64 cores）上以 CPU 執行，每句從新的組字開始，不學習（學習不會影響下一句）。
- 三方都只執行對方未修改的程式：ZhuyinType 用 `zhuyin-cli`；靈犀注音用它的 `0c-server`，經由它文件記載的 socket 協定逐鍵送出；善解用它的評測程式 `shanjie-eval`，以及它的 App 使用的 C 介面（`core/include/shanjie.h`，原始碼未修改，建置成共享程式庫）。`zt systems setup` 依固定的 commit 取得並建置，所有檔案都不放進本專案。
- 靈犀注音的程式是 AGPL-3.0，只建置、執行，沒有複製任何程式碼。善解的評測集依各檔的授權（多為 CC0）讀取，模型檔不放進本專案。
- 各系統同時執行，共用 16 個單執行緒程序（靈犀的選字模型另有一個推論程序），以較低的優先權（nice 10）和主機上的其他工作共用 CPU；每鍵延遲在轉換結束後逐一量測。

## 方法

- 指標是整句全對率：一段輸出和參考答案完全相同才算對。
- 寫法正規化，兩種都套用在所有系統上：
  - S：善解的正規化（她妳它牠嘗周臺裏的合併，加上它的異體字表 `eval/variants.tsv`）。
  - V：ZhuyinType 的 11 組寫法（臺／台、裏／裡等）。
- 我們的集合：每組依固定的種子（7）抽出 4–20 字的漢字段落，最多 400 段，讀音取 ZhuyinType 詞庫最可能的讀音，換成標準鍵盤的按鍵，一聲按空白，最後按 Enter。善解的集合用各列給的讀音；其中沒有讀音的（trap、daily、教育部辭典例句）由善解自己的讀音工具產生。靈犀的案例用案例給的讀音，沒有讀音的由 ZhuyinType 的詞庫產生。
- 每個系統收到同樣的按鍵：ZhuyinType 與靈犀注音逐鍵輸入；善解的評測程式收到同樣的讀音。含打錯的按鍵沒有讀音，善解改由它的 C 介面逐鍵輸入，設定比照它的 App，每鍵之後讓小模型的重排完成再按下一鍵。
- 情境：
  - 沒有前文；
  - 前文：同一行在這段之前的文字（最多 32 字）。靈犀注音的協定只接受它自己送出的文字作為前文，標為 N/A；善解的集合照原樣帶前文時，靈犀注音收到的是沒有前文的同一列（表中註明筆數）；
  - 分兩次送出：在最接近中間的詞界切開，先送出前半，再接著輸入後半；後半的前文是已送出的前半。靈犀注音只對可以學習的送出保留前文，所以這個情境每一句都重新啟動一個空的靈犀程序；
  - 每音節 10% 的機率打錯一個鍵（`zt eval typo` 的產生方式）；
  - 14 種有時間的打錯情境（`zt eval typing-errors`，每組最多 300 段）。按鍵間隔只有 ZhuyinType 使用，其他系統收到同樣順序的按鍵。

## 每鍵延遲

**這些數字是在共用、忙碌的主機上量的，不能互相比較，只是暫時的紀錄；之後會在空閒的主機上另外量測，取代這一節。**

延遲集的 10 句，一個程序、一句一句逐鍵輸入，取每句每鍵時間的 p50、p95 與最大值，再取各句的中位數（毫秒）。各系統的量法也不相同。量測時主機的 1 分鐘負載為 1–13（其他工作同時執行）。

- ZhuyinType：`zhuyin-cli --timing`，引擎程序內處理每一鍵的時間（含神經模型）
- 靈犀注音：經由 socket 一問一答的來回時間；備註是 0c 自己回報的引擎時間（engine_us，含選字模型的等待）
- 善解：經由 C 介面呼叫按鍵的時間；它的 App 在另一個執行緒跑小模型的重排，備註是加上重排的時間

|---|---:|---:|---:|---|
| ZhuyinType | 6.0 | 45.4 | 53.3 | 負載 13 |
| 只用引擎 | 0.65 | 3.4 | 3.6 | 負載 10 |
| 靈犀（統計） | 0.09 | 3.26 | 4.51 | 引擎內 p50 0.01、p95 3.03 ms；負載 2 |
| 靈犀（完整） | 0.09 | 29.77 | 37.79 | 引擎內 p50 0.01、p95 29.55 ms；負載 2 |
| 善解（聊天） | 0.04 | 3.61 | 4.21 | 加上重排 p50 0.04、p95 255.7 ms；負載 2 |
| 善解（正式） | 0.03 | 4.05 | 4.79 | 加上重排 p50 0.04、p95 256.47 ms；負載 1 |

## 限制

- 每一方在自己建立的集合上都有優勢：我們的集合和我們的訓練資料分布相近；善解的集合反映它的詞包與它在開發時遇到的錯誤；靈犀的案例是它的回歸測試。
- 讀音由各集合的建立者產生（我們的集合用 ZhuyinType 的詞庫，善解的集合用善解的），可能偏向建立者支援的讀音。
- 讀音不在詞庫裡、找不到解碼路徑的句子計為錯誤：善解（聊天） 361 筆、善解（正式） 361 筆（所有情境合計，同一句在不同情境重複計算）。
- 靈犀的完整設定在每句結束時的選字模型狀態（所有情境合計）：ready 12849、fallback 905、loading 371。少於一半的句子由模型選字的格子，等主機負載下降後重跑（最多兩次）；其餘退回統計引擎的句子照實計入。
- 善解的評測集中，有些列和我們的訓練資料重疊；去除重疊的子集（「去除重疊」）沿用先前的重疊檢查，這次沒有對最新的訓練資料重新檢查。
- 善解有兩種輸入方式：讀音經由評測程式，按鍵經由 C 介面。兩者的設定一致，但不是同一段程式；「沒有打錯」情境（C 介面）和「沒有前文」（評測程式）可以對照兩者的差異。
- 「不支援」的格子是對方沒有這項設計的情境，只輸入 50 句作為樣本，不做成對檢定，也不標粗體。注音按鍵依聲母、介音、韻母的位置組成音節，所以音節內的對調在任何注音輸入法多半仍能打對；其他的打錯則需要容錯的設計。
- 按鍵間隔只有 ZhuyinType 使用；其他系統沒有這項輸入。
- 靈犀注音有選用的「不打聲調」，這次維持它的預設（關閉），所以一聲不按空白的情境也標為不支援。
- 這是一次量測，各方的版本與設定都會更新。靈犀注音用的是 v0.2.6 的發布資料，不代表它最新的版本。
- 只比整句全對率與每鍵延遲。記憶體、補全、補標點、不打聲調等功能沒有比較；各專案公布的數字見 [相關工作](../research/related-work.md#設計上的差異)。

## 重現

```sh
tools/zt --remote systems setup                     # 依固定的 commit 取得、建置靈犀注音與善解
tools/zt --remote --nice 10 --export --detach \
  --push data/build/homophone2/test_zai.txt --push data/build/homophone2/dev_zai.txt \
  bench compare                                     # 全部系統 × 全部集合；中斷後再執行會接著做
tools/zt remote pull docs/benchmarks/competition.json
tools/zt bench compare --render                     # 由紀錄檔產生這一頁
```

紀錄檔 [competition.json](competition.json) 保存這一頁的數字：每格兩種正規化的整句全對率、句數、成對檢定、延遲摘要與各系統的版本。每個系統對每一句的輸出保存在完整的紀錄檔（`data/build/bench/compare/main/record.json`，不放進版本庫）。做法見 `ml/src/zhuyintype_ml/eval/systems/README.md`。
